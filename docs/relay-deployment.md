# Relay Deployment

TypeKart internet play uses a WebSocket relay. The relay routes room-scoped protocol envelopes between an authoritative host and joiners. It does not run game rules, store accounts, or perform matchmaking.

## Local Development

Start a local relay:

```sh
cargo run -- relay --bind 127.0.0.1:8080
```

Useful hardening flags:

```sh
cargo run -- relay \
  --bind 127.0.0.1:8080 \
  --max-rooms 256 \
  --max-participants-per-room 5 \
  --max-message-bytes 262144 \
  --room-idle-timeout-secs 7200
```

Host through that relay:

```sh
cargo run -- host --name host --relay ws://127.0.0.1:8080
```

Join using the room code printed by the host:

```sh
cargo run -- join --name player2 --relay ws://127.0.0.1:8080 --room rocket-salad-tiger
```

## Local Network Relay

To let other computers on the same LAN use your relay, bind it to all interfaces:

```sh
cargo run -- relay --bind 0.0.0.0:8080
```

Then host and join using the relay machine's LAN address:

```sh
cargo run -- host --name host --relay ws://192.168.1.25:8080
cargo run -- join --name player2 --relay ws://192.168.1.25:8080 --room rocket-salad-tiger
```

## Public Relay

For public internet play, run the Rust relay as a plain `ws://` service on localhost and put a TLS reverse proxy in front of it.

Recommended shape:

```text
players -> wss://relay.example.com -> reverse proxy -> ws://127.0.0.1:8080
```

The TypeKart client supports `wss://` relay URLs. The Rust relay binary currently does not terminate TLS directly.

Example public commands:

```sh
typekart host --name host --relay wss://relay.example.com
typekart join --name player2 --relay wss://relay.example.com --room rocket-salad-tiger
```

The released CLI defaults to the public TypeKart relay at `wss://typekart-relay.fly.dev`, so `--relay` is only required for custom relay deployments.

## Reverse Proxy

Caddy is the simplest deployment target because it manages certificates automatically:

```caddyfile
relay.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Run the relay bound only to localhost on the server:

```sh
typekart relay --bind 127.0.0.1:8080
```

## Docker

Build the image:

```sh
docker build -t typekart-relay .
```

Run the relay locally:

```sh
docker run --rm -p 8080:8080 typekart-relay
```

Run with explicit limits:

```sh
docker run --rm -p 8080:8080 typekart-relay \
  typekart relay \
  --bind 0.0.0.0:8080 \
  --max-rooms 128 \
  --max-participants-per-room 5 \
  --max-message-bytes 262144 \
  --room-idle-timeout-secs 3600
```

For cloud deployment, expose container port `8080` to your platform's HTTP/WebSocket routing layer. Use the platform TLS endpoint or a reverse proxy for public `wss://`.

## Fly.io

The repository includes `fly.toml` for a single-machine relay deployment.
It runs the relay on `0.0.0.0:8080` and configures Fly to check
`GET /healthz`.

First-time setup:

```sh
fly launch --no-deploy
```

If Fly asks whether to overwrite `fly.toml`, keep the checked-in file unless you intentionally want a different app name or region.

Deploy:

```sh
fly deploy
fly scale count 1 --yes
```

The default app name in `fly.toml` is `typekart-relay`. Fly app names are globally unique, so you may need to change:

```toml
app = "your-typekart-relay-name"
```

Then players can use:

```sh
cargo run -- host --name host --relay wss://your-typekart-relay-name.fly.dev
cargo run -- join --name player2 --relay wss://your-typekart-relay-name.fly.dev --room rocket-salad-tiger
```

The Fly deployment must run exactly one machine because relay rooms are in memory. If multiple machines are started, hosts and joiners can be routed to different machines and joins will intermittently fail with "room not found". Verify after deploy:

```sh
fly status -a your-typekart-relay-name
```

The relay answers `GET /healthz` with `200 OK` before the WebSocket handshake.
Game traffic still uses WebSocket upgrade requests on the same port.

## Render

The repository includes `render.yaml` for Render Blueprint deployment.

Deployment path:

1. Push this repository to GitHub.
2. In Render, create a new Blueprint from the repository.
3. Confirm the `typekart-relay` web service.
4. Render builds the Dockerfile and exposes the service over HTTPS/WSS.

Players can use the Render service URL as the relay:

```sh
cargo run -- host --name host --relay wss://typekart-relay.onrender.com
cargo run -- join --name player2 --relay wss://typekart-relay.onrender.com --room rocket-salad-tiger
```

Render service URLs vary by account and service name. Use the actual URL shown in the Render dashboard.

## Operational Limits

- The relay is stateful and in-memory. Restarting it closes all rooms.
- Room codes are generated by the relay.
- The host remains authoritative; if the host disconnects, the room closes.
- All racers must run the same TypeKart version as the host. The relay rejects mismatched joiners before forwarding them to the host.
- The relay enforces configurable room count, participants per room, message size, and idle timeout limits.
- There is no authentication, moderation, reconnect, spectator mode, or matchmaking.
- Snapshot traffic is currently forwarded at the same rate as LAN play.
- Use a process supervisor such as `systemd`, `launchd`, Docker restart policy, or a platform service manager for long-running deployments.

## Validation Checklist

1. Start `typekart relay --bind 127.0.0.1:8080`.
2. Run `host` against `ws://127.0.0.1:8080`.
3. Run `join` against the printed room code.
4. Ready both players and start a race.
5. Repeat through a LAN IP from a second machine.
6. Repeat through `wss://` after configuring the public reverse proxy.
